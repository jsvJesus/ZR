# Персонажи Stalker Online: исследование прямого чтения

Дата: 2026-10-27.

## Задача

Читать оригинальные модели, скелеты, анимации и текстуры из
`bin/packs/characters2`, без предварительной конвертации ресурсов.
Восстановить locomotion по исходным данным и скриптам из `sdk/scripts`.
Этот документ фиксирует исследование и предложение по реализации;
загрузчик и воспроизведение персонажа пока не реализованы.

## Что проверено на локальных файлах

| Ресурс | Количество файлов |
| --- | ---: |
| `.model` | 922 |
| `.visual` | 932 |
| `.primitives` | 934 |
| `.animation` | 833 |
| `.dds` | 1561 |

Проверочное чтение бинарного дерева успешно прошло на всех 922 `.model`
и 932 `.visual`. Это проверка структуры контейнера; корректность геометрии,
материалов и анимационного воспроизведения таким чтением не подтверждается.
Оригинальные ресурсы не изменялись.

Базовая модель, указанная в `sdk/scripts/client/StalkerModel.pyc_dis:60`:
`characters2/basemodel/StalkerBase2.model`.

В ней прочитаны:

- 597 описаний анимаций; все 597 ссылок `nodes + .animation` существуют
  относительно `bin/packs`.
- 660 описаний действий `action`; у 138 есть секция `match`.
- `frameRate`, `NodePriority`, события `cues`, параметры действий и ссылки
  на визуальную модель.
- В `StalkerBase2.visual` прочитаны 113 узлов иерархии. Это общее число
  узлов, включая вспомогательные узлы; его нельзя считать числом костей,
  непосредственно влияющих на вершины.

## Форматы и зависимости

`.model`, `.visual` и `sdk/scripts/common/capabilities.xml` здесь содержат
бинарное дерево с сигнатурой `45 4E A1 62` и байтом версии `00`.
После заголовка находятся таблица имён и секции с типизированными значениями.
Нужны повторяющиеся дочерние секции и сохранение их порядка:
обычный словарь по имени потеряет действия, анимации и группы геометрии.

На проверенных данных читаются строки, целые числа, float-векторы,
логические значения и представление строк через Base64. Например,
`AutogunArmed` в capabilities хранится через последний вариант.
Собственное значение секции также значимо: числовой идентификатор
capability хранится у `state`, а `name` и `id` — в дочерних секциях.

`StalkerBase2.primitives` начинается с `65 4E A1 42`.
В нём обнаружено имя формата вершин `xyznuviiiwwtb`.
Раскладка вершин, индексов и таблицы секций ещё не проверена декодером.

Визуальная модель содержит иерархию узлов, renderSet, ссылки на потоки
вершин/индексов и палитру узлов для renderSet. Привязку вершин необходимо
сопоставлять именно с соответствующей палитрой.

`.animation` — отдельный бинарный формат. Например,
`animation2016/walk_forward.animation` начинается с float `30.0`,
затем содержит строки с длиной и именем `walk_forward`.
Смысл первого поля, структура каналов, единицы времени и интерполяция
ещё требуют проверки. По одному заголовку нельзя выбирать частоту кадров.

В `.model` имеются параметры материалов `dye/tint`; в `.visual` встречаются
ссылки на оригинальные `.fx` и текстуры. Для изображения в DX11 нужны
соответствующие материалы и шейдеры проекта. Исходные `.fx` нельзя считать
автоматически совместимыми с существующим рендерером.

Пути имеют корень `bin/packs`, например `characters2/...`.
Некоторые материалы ссылаются на ресурсы вне `characters2`, например
`textures/default/white.dds`. Полная проверка зависимостей ещё не выполнена.

## Откуда восстанавливать locomotion

| Источник | Данные и поведение |
| --- | --- |
| `StalkerBase2.model` | Действия, animation, match/trigger/cancel, capsOn/capsOff, диапазоны скорости и углов, track, blendInTime/blendOutTime, NodePriority, cues |
| `sdk/scripts/common/capabilities.xml` | 27 состояний с исходными идентификаторами; номера не образуют непрерывную последовательность |
| `sdk/scripts/client/AnimationCaps.pyc_dis` | Работа со списком `model.motors[0].matchCaps` |
| `sdk/scripts/client/Avatar.pyc_dis` | Обновление состояний и реакция на загрузку модели |
| `sdk/scripts/client/player_speed_settings.pyc_dis` | Скорости, сглаживание, ограничения поворотов, настройки камеры |
| `sdk/scripts/client/player_movement.pyc_dis` | Выбор скоростей и взаимодействие движения с физикой, коллизиями и уклонами |
| `sdk/scripts/client/new_turn.pyc_dis` | Повороты на месте, пороги углов, связь корпуса и ног; Python-вариант и обёртка нативного варианта |
| `sdk/scripts/client/AvatarTrackers.pyc_dis` | Параметры разворота корпуса и ног, трекеры верхней части тела |
| `sdk/scripts/client/avatar_jump.pyc_dis` | Управление прыжком |
| `sdk/scripts/client/animation_jump_config.pyc_dis` | Фазы прыжка, выбор по кадру и скорости, варианты приземления |
| `sdk/scripts/client/StalkerModel.pyc_dis` | Сборка персонажа из базовой модели и частей одежды/тела |
| `sdk/scripts/client/Tests/ActionMatcher.pyc_dis` | Исходный инструмент визуализации trigger/cancel и диагностики matcher |

Примеры исходных настроек: `MAX_SPEED.SPRINT = 6.3`,
`BORED_WALK = 1.3`, `BORED_RUN = 3.6`.
Это значения конфигурации, а не универсальные скорости любого состояния:
есть отдельные варианты для оружия, приседа, ранения, движения назад и вбок.

Пример реально прочитанного правила `slope_down_armed_fw`:
анимация `slope_down`, скорость от `3.0` до примерно `16.7`,
`minModelYaw = -20`, `maxModelYaw = 20`, `capsOn = 12`, `capsOff = "5 14"`.
Правила следует читать из ресурсов, сохраняя исходный порядок,
а не создавать заново по названиям файлов анимаций.

## Что пока ограничивает точность восстановления

В `new_turn.pyc_dis` есть прямой вызов
`BigWorld.actionMatcherAdvancedTurnSettings(TURNS)` и настройка нативного
motor. Значит, скрипты задают параметры и часть алгоритмов, но сами по себе
не содержат всю реализацию движка. Порядок выбора подходящих действий,
гистерезис trigger/cancel, смешивание, продвижение движения и угла из
анимации нужно подтверждать отдельно.

`sdk/scripts/client/PlayerAvatar.pyc` присутствует, но рядом лежит пустой
`PlayerAvatar.pyc_dis_failed`, успешной декомпиляции этого модуля не найдено.
Нельзя считать, что код локального управления полностью восстановлен.
Нужно отдельное чтение байткода или другой подтверждающий источник.

Совпадение locomotion с оригиналом должно проверяться на одинаковых
последовательностях ввода, скоростях, переходах состояний и времени.
Воспроизведение оригинального клипа само по себе такого совпадения не доказывает.

## Предложение по реализации

Один общий читатель исходных ресурсов и анимационное ядро в `World`,
доступные редактору и клиенту. Графические буферы и отрисовка остаются
в соответствующем приложении. Декодирование в структуры оперативной памяти
и загрузка в GPU выполняются при чтении; промежуточные файлы ресурсов
не создаются.

1. Общий читатель бинарных секций, затем `.model`/`.visual` с проверкой
   границ, ссылок, типов, наследования и порядка секций.
2. Декодеры `.primitives` и `.animation`, проверка матриц, палитр,
   bind pose, весов, каналов и временной шкалы на реальных файлах.
3. Сборка видимого персонажа из частей, чтение DDS существующим кодом,
   скиннинг и необходимые материалы.
4. Проигрыватель одиночных анимаций, слои, приоритеты костей, события,
   смешивание и обработка движения корня.
5. Восстановление matcher по данным `.model`, затем состояний,
   исходных скоростей, поворотов и фаз прыжка по скриптам.
6. Сравнение с оригиналом и уточнение тех правил, которые реализованы
   нативным движком и ещё не подтверждены.

Пользователь выбрал первый интерфейс: кнопка Play в редакторе,
появление персонажа в месте текущей камеры и камера от третьего лица.
Сейчас клиент содержит только базовое окно MonoGame, редактор уже
отображает Terrain через DX11.

Дизайн первого этапа:
`docs/superpowers/specs/2026-10-27-editor-play-character-design.md`.
До разработки требуется согласование описанного там поведения и границ.
